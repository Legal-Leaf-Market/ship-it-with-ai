Build a booking workflow

Map one job from inquiry to confirmed booking, using the same pattern behind the Crossroads case study.

On this page

  1. Map the handoffs
  2. Give the job one ID
  3. Define who can update it
  4. Test events out of order

1. Map the handoffs

Start with one booking type. Write down who owns each step, which record they update, and what proves the step is complete.

StepEvidence
Inquiry receivedContact, requested date, and booking ID
Agreement preparedAgreement version and date sent
Agreement signedSignature and timestamp
Deposit confirmedAmount, confirmation time, and payment reference

2. Give the job one ID

Use a stable booking ID across the inquiry, agreement, and payment records. Keep signature and deposit status separate. Decide what a confirmed booking means for your business. In this example, it requires both a signed agreement and a confirmed deposit.

Booking: DEMO-001
Agreement: Draft | Sent | Signed
Deposit: Outstanding | Confirmed
Confirmed booking: agreement signed AND deposit confirmed

3. Define who can update it

Let the team record when the agreement goes out and accept the signer’s action through the agreement tool. Confirm the deposit from a payment provider’s confirmed event or a staff reconciliation. Opening a payment link alone should leave the deposit outstanding. Keep a timestamp and reference for each change.

4. Test events out of order

Try the deposit first, then the signature. Repeat each update to check that it doesn’t create a duplicate charge or record. Try a failed payment and an unsigned agreement. In all three cases, compare what staff see against the underlying records.
